## What we apply

| Technique | How our deck uses it |
|---|---|
| First 15 seconds: team name, then straight into the pain; no agenda slide | Slide 1 opens with one sentence of value, then Somchai |
| One specific patient, not an abstract system | Somchai, 58, used to play tennis, now has high blood pressure |
| MIT Hacking Medicine "mad lib": we improve [metric] for [population] who suffer [pain]; today they [workaround], but [failure]; we attack it by [approach] | Spoken in slide 1–2 |
| 5–7 slides for 3 minutes, one idea per slide, visuals over bullets | 7 slides, each title is a claim |
| 1–2 well-sourced numbers, no invented market sizes or accuracy claims | 93% / 15% (Italian GPs), 12.5% rehab attendance (single Thai site); synthetic test results labelled |
| Show the demo by 1:00; one unbroken user journey | Demo starts 1:15: tennis → badminton or bowling |
| Always have an offline backup of the demo | Slide 4 is a storyboard of the demo, usable if the live page fails |
| Technical judges: a clean architecture slide naming FHIR, IRIS, vector storage, model stack, guardrails | Slide 5 |
| Say what was built at the event versus reused | Slide 5 footer: built vs reused |
| End on one rehearsed sentence; ask for pilot access, mentorship, sandbox, not money | Slide 7 |
| One main presenter, or two with a fixed hand-off; Q&A owners by topic | `pitch/README.md` speaker table |
| Rehearse to 2:50 with a timer, 10 s buffer | README checklist |

## Mistakes to avoid
Burying the demo past one minute · showing every feature · relying on venue Wi-Fi · walls of text · unsupported numbers · a chaotic architecture slide · talking over each other in Q&A · ending with "that’s it, thanks".
